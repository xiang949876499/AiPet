# 宠店 AI 管家 — 统一工作台 UX 重构设计

> 将碎片化的十几个独立页面重构为一个有统一设计语言、角色感知、可操作的运营工作台
> 日期：2026-06-23 | 状态：待实施
> 依赖：无（纯 Web 层改造，后端 API 不变）

---

## 一、问题诊断

### 1.1 用户反馈

通过与用户对话确认了以下核心痛点：

| 问题 | 表现 |
|------|------|
| 流程碎片化 | 十几个独立页面，用户不知道去哪里找功能——"话术不知道在哪生成" |
| 界面不专业 | 裸 Jinja2 模板，每个页面各自为政，没有组件库、没有品牌感 |
| 操作太散 | 导入客户 → 看提醒 → 看推送 → 看内容日历 → 看数据，全在不同页面 |
| 无角色感知 | 老板和店员看到同一套界面，该隐藏的数据没隐藏，该突出的行动没突出 |
| 无引导 | 新人打开后对着指标发呆，不知道第一步该做什么 |
| 无移动端适配 | 宠物店老板和店员的主要设备是手机，但平台是桌面 Web only |

### 1.2 设计目标

- **一个统一工作台**：所有操作在一个 Shell 框架内完成，不需要在十几个页面之间导航
- **三个角色视图**：老板看营收+数据、店员看待办+操作、管理员看系统设置
- **一套设计语言**：统一的配色、组件、间距、排版，专业感
- **可操作首页**：首页不是数据仪表盘，而是"每日三件事"的待办面板
- **引导式入门**：4 步 Wizard 让新用户 3 分钟完成首次设置

### 1.3 与现有 Phase 1 设计的关系

本文档是对 [2026-06-22 Phase 1 补充设计](./2026-06-22-pet-store-optimization-phase1-supplement.md) 的 UX 层补充。Phase 1 文档回答了"做什么功能"，本文档回答"怎么让产品好用"。两个文档共同构成 V1.1 完整设计。

功能层面完全沿用 Phase 1 设计，本文档只改造 Web 模板层的呈现方式。

### 1.4 明确不做的范围

- ❌ 不引入前端框架（React/Vue/Svelte）
- ❌ 不引入 CSS 框架（Tailwind/Bootstrap）——用纯 CSS 自定义属性
- ❌ 不做微信小程序
- ❌ 不引入图表库（纯 CSS/HTML 简易图表）
- ❌ 不新增 Python 依赖包
- ❌ 不做全自动发帖/私信（平台风控风险）
- ❌ 不做 AI 视频生成
- ❌ 不做完整收银/进销存/库存管理
- ❌ 不做宠物医疗诊断

> **注**：新增的 6 个功能模块（§十）涉及少量后端 Agent 和 2 个新数据模型，但复用现有 `agents/` 和 `core/llm.py` 架构，不打散现有代码结构。

## 二、整体架构：统一 Shell

### 2.1 目标架构

统一工作台 = **一个 Shell 骨架 + 角色化导航 + 统一设计 Token**

```
┌─────────────────────────────────────────────────────────────┐
│  🐾 宠店 AI 管家    [搜索客户...]    🔔 3    👤 老板  [退出]  │  ← 全局顶栏（固定）
├──────────┬──────────────────────────────────────────────────┤
│          │                                                  │
│ 📋 今日   │                                                  │
│ 👥 客户   │                                                  │
│ ✉️ 触达   │              内容区域                             │
│ 📱 内容   │          （根据导航 + 角色渲染）                    │
│ 📊 看板   │                                                  │
│ ─────── │                                                  │
│ ⚙️ 设置   │                                                  │
│          │                                                  │
└──────────┴──────────────────────────────────────────────────┘
```

### 2.2 导航结构（按角色裁剪）

| 导航项 | 老板 | 店员 | 说明 |
|--------|:----:|:----:|------|
| 📋 **今日** | ✅ | ✅ | 首页，角色化"每日三件事" |
| 👥 **客户** | ✅ | ✅ | 客户列表 + 详情 + 导入 |
| ✉️ **触达** | 全部 | 待确认 | 老板看全部，店员只看自己待处理的 |
| 📱 **内容** | ✅ | 只读 | 内容日历 + 模板 |
| 📊 **看板** | ✅ | ❌ | 数据分析，店员不可见 |
| ⚙️ **设置** | 完整 | 仅个人 | 老板配置规则/系统，店员只改自己 |

### 2.3 技术实现

- **Shell 模板**：`web/templates/_layout.html` 作为基模板，使用 Jinja2 `{% block %}` 继承
- **导航状态**：服务端渲染当前 active 状态，通过 CSS class 高亮
- **响应式**：左侧导航在手机端收起到汉堡菜单（`< 768px` 时）
- **全局顶栏**：搜索框（搜索客户名/宠物名）、通知铃铛（待处理触达数）、当前用户+角色名
- **角色裁剪**：FastAPI 中间件 + Jinja2 条件渲染
- **文件结构**：

```
web/
├── templates/
│   ├── _layout.html          ← 新增：Shell 基模板
│   ├── _workbench_nav.html   ← 已有，需重构为侧栏导航
│   ├── dashboard.html        ← 改造：嵌入 Shell + 每日三件事
│   ├── customers.html        ← 改造：嵌入 Shell + UI 翻新
│   ├── customer_detail.html  ← 改造：嵌入 Shell + Tab 布局
│   ├── content_calendar.html ← 改造：嵌入 Shell
│   ├── outreach_confirm.html ← 改造：合并触达三页面
│   ├── login.html            ← 保持独立（不需 Shell）
│   ├── activate.html         ← 保持独立（不需 Shell）
│   └── ...
└── static/
    ├── app.css               ← 新增：全局设计系统
    └── app.js                ← 新增：Shell 交互（搜索/通知/移动菜单）
```

### 3.2 组件规范

**按钮** — 三级体系：
- **主按钮** `.btn-primary`：实心 Indigo 背景，白色字。一个页面最多一个
- **次按钮** `.btn-secondary`：Indigo 边框 + Indigo 字，透明背景
- **幽灵按钮** `.btn-ghost`：无边框无背景，用于表格行内操作

**卡片** `.card`：
```
┌──────────────────────────┐
│ 标题               [操作]│  ← .card-header: 16px padding, border-bottom
├──────────────────────────┤
│                          │
│ 内容区                   │  ← .card-body: 16px padding
│                          │
└──────────────────────────┘
```

**数据指标卡** `.metric-card`：
```
┌─────────────────────┐
│ 🤖 AI 推荐待跟进     │  ← 标签
│       8 人           │  ← 32px 大数字
│   较昨日 +2 ↑        │  ← 13px 趋势标注
└─────────────────────┘
```

**状态标签** `.tag`：
| 状态 | 样式 |
|------|------|
| 待处理 / 待确认 | Amber 浅底 + Amber 深字 |
| 已发送 / 已完成 / 活跃 | Emerald 浅底 + Emerald 深字 |
| 失败 / 已取消 | Red 浅底 + Red 深字 |
| 免打扰 / 已跳过 | Gray 浅底 + Gray 深字 |

**表格** `.table`：
- 表头：灰色背景 `#F3F4F6`，uppercase 小字
- 行悬停：浅 Indigo 背景
- 最后列固定为操作按钮列（右对齐）

### 3.3 页面统一骨架

每个内容页面遵循：
```
┌──────────────────────────────────────┐
│ 页面标题               [主操作按钮]  │  ← Page Header
├──────────────────────────────────────┤
│ [Tab/筛选区] 或 [指标卡行]            │  ← 可选
├──────────────────────────────────────┤
│ 主内容区（表格/卡片/表单）             │
├──────────────────────────────────────┤
│ 分页/底部信息                         │
└──────────────────────────────────────┘
```

### 6.3 决策卡片结构

每条触达任务包含可解释的决策卡片：

```yaml
trigger_rule: "洗护周期到期"
evidence:
  last_grooming_date: "2026-05-28"
  days_since: 25
  suggested_cycle: 21
customer_context:
  name: "豆豆妈妈"
  tier: "VIP"
  total_spent: 6200
  visit_count: 12
  recent_response_rate: "100% (3/3)"
suggestion: "上次做的是精剪造型，建议在话术中提及保持造型效果"
```

### 6.4 Tab 映射

| Tab | 数据来源 | 状态筛选 |
|-----|----------|----------|
| 待生成话术 | FollowTask | `status='待处理' AND ai_message IS NULL` |
| 待确认 | FollowTask | `status='待处理' AND send_mode='manual_confirm' AND ai_message IS NOT NULL` |
| 待发送 | PushTask | `status='approved'` |
| 已发送 | PushTask + OutreachLog | `status IN ('sent', '已发送')` |

### 6.5 UI 交互

### 10.1 门店营销体检报告

**定位**：获客钩子——¥199/次的低价引流产品，让老板在付费前先感知 AI 价值。

│                                           │

### 10.2 活动方案生成器

**定位**：营销增值功能——不只会写话术，还会策划完整活动。

**支持活动类型**：

| 类型 | 示例 |
|------|------|
| 🆕 新客引流 | 首次洗护体验价 + 到店礼 |
| 🔄 老客复购 | 45天未到店客户专属券 |

| 👥 裂变活动 | 老带新双方得护理券 |

**技术要点**：

### 10.4 每周复盘报告

- 专业版+可推送至老板企业微信
- 入口：看板页「📅 周报」Tab

**数据模型**：复用现有 `ContentItem`（`content_type = "weekly_report"`）或新建轻量表。

> **设计原则**：Credit 远大于实际需求，让用户感知"用不完"。实际约束来自后端模型路由和成本控制，而非前端额度。

**前端展示**：从"剩余 AI 调用 X 次"改为"本月已用 X / Y Credit"

**实现方式**：复用 `StoreSubscription.ai_quota_used`，每次任务完成后按规则累加。

**成本控制（后端）**：
- 每个任务最多生成 3 个版本
- 每个任务最多修改 3 轮
- 长报告（体检、周报）异步生成，可用 Batch API 降本
- 店铺画像缓存（`Store.settings` JSON），减少重复上下文

## 十三、响应式断点

| 断点 | 宽度 | 行为 |
|------|------|------|
| 桌面 | ≥ 1024px | 完整侧栏 + 表格视图 |
| 平板 | 768px – 1023px | 侧栏收起为图标模式 + 表格横向滚动 |
| 手机 | < 768px | 侧栏变为底部 Tab 栏 + 全卡片布局 |

响应式实现使用 CSS media query，不依赖 JavaScript 框架。

## 十四、设计决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 前端技术 | 纯 Jinja2 + CSS，不引入框架 | 保持项目轻量，不增加构建步骤和新依赖 |
| CSS 方案 | 纯 CSS 自定义属性 | 设计 Token 集中管理，方便未来换主题 |
| 图表方案 | 纯 CSS/HTML 简易图表 | 不引入图表库依赖，保持轻量 |
| Shell 实现 | Jinja2 模板继承 | 与现有技术栈一致，服务端渲染 |
| 触达页面 | 三页合一 + Tab | 减少用户导航困惑，流程更连贯 |
| 首页设计 | "每日三件事"可操作面板 | 从数据展示升级为行动指导 |
| 角色权限 | 三角色模型（老板/店员/管理员）| 覆盖宠物店实际人员结构 |
| 移动端 | 响应式 Web，不做原生 App | 开发成本可控，后续可迭代为 PWA |
| 改造范围 | UX 重构纯 Web 模板层；新增功能涉及轻量 Agent 和 2 个模型 | 新增 Agent 复用现有 agents/ 架构，模型遵循现有 SQLAlchemy 模式 |
| 新增功能选型 | 取四份文档交叉验证的前 6 个 | 被多份独立分析共同指向=需求真实存在 |
| 门店体检报告 | ¥199/次低价获客，非主利润 | 让老板在付费前先感知 AI 价值 |
| 活动方案生成 | 覆盖 7 种活动类型，单次 Prompt 输出完整方案 | 宠物店高频需求，一次生成降低使用门槛 |
| 点评回复 | 纯文本 + 人工确认 | 成本极低，本地生活商家刚需 |
| AI 经营问答 | 种子知识库 + RAG，不回答医疗问题 | 提升日常实用性，合规边界清晰 |
| Credit 额度 | 用 credit 统一用户感知，后端模型路由控成本 | 不对外暴露 token 概念，用户不用理解技术细节 |
| 定价策略 | 体验版 ¥19 引流 + 增长版 ¥1999 主推 | 文档 2 和文档 3 共同指向的低价引流+高价主力模式 |
